---
title: Credential security
description: How the server stores and protects connector credentials, OAuth client secrets, and API tokens.
---

The server holds secrets on behalf of an organization: tokens and keys for external tools, OAuth client secrets, and bearer tokens for its own API. Two rules govern all of them. A secret is stored encrypted or hashed, never in plain text. And no API response, log line, or redirect URL ever carries secret material.

## What the server stores

| Secret | At rest | Notes |
| --- | --- | --- |
| Connector credentials (OAuth tokens, API keys) | Envelope-encrypted | Decrypted only at the moment of use. |
| Client registration secrets (customer OAuth apps) | Envelope-encrypted | Platform registrations store no secret at all—the row points at a platform-owned app. |
| Service credentials (`trema_sc_` API tokens) | SHA-256 hash | The secret renders exactly once, at creation. |
| Bootstrap token | SHA-256 hash | Dedicated-mode first boot only. |
| OAuth flow state | SHA-256 hash | Single use, 15-minute expiry. |
| Sign-in passwords | Hashed by the auth layer | Applies to sign-in with email. Set `TREMA_PASSWORD_AUTH_ENABLED=false` to turn it off. |

Connector credential rows keep refresh bookkeeping—success and failure timestamps, an attempt counter, an exhausted flag—outside the ciphertext. These columns carry no secret material and let operators see credential health without a decryption.

## Envelope encryption

Every encrypted secret gets its own random 256-bit data key. AES-256-GCM encrypts the payload with the data key, then encrypts the data key with the master key. The stored value is one versioned envelope holding both ciphertexts, their nonces, and their authentication tags. GCM authentication makes tampering detectable: a modified envelope fails decryption instead of yielding altered plaintext.

Per-secret data keys keep key rotation a re-wrap: rotating the master key means re-encrypting the small wrapped keys, not every payload.

## `TREMA_CREDENTIAL_MASTER_KEY`

The master key is a base64-encoded 32-byte value from the environment:

```sh
openssl rand -base64 32
```

The server starts without it, but every operation that stores or reads an encrypted secret fails with a configuration error until it is set. There is no plaintext fallback.

Treat the key like the database credentials: losing it makes stored connector credentials unrecoverable, and every affected connector must be reconnected. Back it up with the same care as the database itself.

## Connect-flow protections

The OAuth authorization-code flow and static credential entry apply these controls:

- The `state` parameter is 32 random bytes. The server stores only its hash, consumes it atomically on first use, and rejects replays and states older than 15 minutes.
- PKCE with the S256 challenge is on by default; the provider catalog opts out only where a provider does not support it.
- One callback URL serves the whole deployment—`<TREMA_AUTH_BASE_URL>/connect/callback`—registered once in each OAuth app.
- After the callback, the browser is redirected only to origins listed in `TREMA_WEB_ORIGINS`; any other return URL falls back to the first configured origin.
- API keys and basic credentials are verified against the provider before they are stored. A credential that fails verification is never written.
- Token-exchange and verification failures surface as typed errors that do not include the upstream response body, which can echo tokens.

## API responses

Registration and credential endpoints require the `manage_connectors` capability, held by owners and admins at the relevant scope. Responses carry metadata only: identifiers, auth mode, expiry, validity flags, and refresh bookkeeping. No response includes a token, a client secret, or ciphertext.

The organization's agent principal holds no control-plane role, so a service credential bound to it cannot reach any of these endpoints.

## Revocation

Revoking a connector credential marks the row; listings report it as invalid from that moment. Deleting a client registration removes the stored client secret with it. Revoking a service credential takes effect on the next API call—the hash lookup fails immediately.
